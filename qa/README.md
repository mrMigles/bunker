# QA: E2E-сценарии «ГЛУБЖЕ»

Набор сценариев для ручного/агентного E2E-тестирования игры **через браузер, как обычный игрок**. Это не unit- и не integration-тесты: агент запускает игру, играет, делает скриншоты, визуально сравнивает результат с ожидаемым и заводит issues (баги и улучшения). Другой агент исправляет, затем прогон повторяется.

Этот этап — только сценарии. Игру здесь не исправляем.

## Подготовка стенда

```bash
pnpm i
```

```bash
pnpm dev
```

- Клиент: <http://localhost:5173>, сервер: `ws://localhost:2567`. Для агента в приложении Claude есть конфигурация `dev` в `.claude/launch.json`.
- Для каждого прогона создавайте **новый бункер** (новое имя игрока, например `QA-<ID сценария>`), если в сценарии не сказано иное. Так прогоны не мешают друг другу.
- Сохранения лежат в `packages/server/data/saves.sqlite`. Для прогона «с нуля» можно остановить сервер и удалить файл. Спросите разрешения, если база не ваша.

### Как быстро попасть в нужное состояние (только dev)

Отладка нужна **только чтобы дойти до предусловия**. Проверять результат нужно через обычный интерфейс: кликами, касаниями и клавишами, как игрок. Если сценарий проверяет путь, по которому игрок доходит до состояния, отладку не используйте.

| Нужно | Как |
|---|---|
| Пропустить пролог | В лобби у хоста галочка «Без пролога» |
| Отладочная панель | Клавиша `~` в бункере |
| Время суток | `__net.send({ k: "debug", op: "hour", arg: 21.8 })` (или кнопки «⏰ 12:00», «⏰ 21:48» в панели) |
| Сразу ночь (совет) | `op: "night"` / «🌙 Ночь» |
| Ресурсы | `op: "rich"` («💰 Ресурсы»); точечно — `op: "res", arg: { food: 0, water: 0 }` |
| Вылечить всех | `op: "heal"` |
| Скорость времени | `op: "speed", arg: 10` / `arg: 1` |
| Технологии | `op: "tech", arg: "<id>"`, `op: "alltech"` |
| Заметность (для налёта) | `op: "notice", arg: 80`; налёт — кнопки «🏴 Налёт» и «🚇 Налёт из метро» в панели |
| Событие | `op: "event", arg: "<id события из shared/src/data/events/*.json>"` |
| Опыт (левел-ап) | `op: "xp", arg: 500` |
| Все настолки / сесть за стол | `op: "games"`, `op: "sit"` |
| Тестовый бой | Кнопка «Тестовая арена» в лобби (у хоста) или `__net.send({ k: "debugArena" })` |
| Состояние мира | `__net.pub` (общий вид), `__net.priv` (приватный), `__net.myChar()` (свой персонаж), `__game` (корневой UI) |

Если отладка не работает (например, собрано с `NODE_ENV=production`), доходите до состояния обычной игрой и отметьте это в отчёте.

## Режимы (viewport / device)

Каждый подходящий сценарий проходится **минимум** в режимах `D`, `MP`, `ML`, `TG-P`. Остальные — где указано в сценарии или если в основном режиме что-то выглядит на грани.

| Код | Режим | Размер | Как эмулировать |
|---|---|---|---|
| `D` | Desktop browser | 1440×900 | Обычное окно, мышь и клавиатура |
| `D-S` | Небольшой ноутбук | 1280×720 | То же |
| `MP` | Mobile portrait | 390×844 | `hasTouch`, `isMobile`, `?mobile=1`. Управление только касаниями, без клавиатуры |
| `MP-S` | Маленький телефон, портрет | 360×640 | То же |
| `XS` | Минимальный viewport | 320×568 | То же. Цель — не «красиво», а «можно играть и ничего не потеряно» |
| `ML` | Mobile landscape | 844×390 | То же |
| `ML-S` | Худший альбомный случай (браузер с адресной строкой) | 760×300 | То же. Под этот размер рассчитана раскладка (README) |
| `TG-P` | Telegram WebApp на телефоне | 390×700 (окно WebApp меньше экрана) | Заглушка `window.Telegram.WebApp` с `platform: "android"`, мобильный UA, `contentSafeAreaInset` ≠ 0, вход по `?mobile=1&tg=<token>`. Токен: `GET http://localhost:2567/api/tg/dev-token?chat=<id>&user=<id>&name=<имя>`. Пример заглушки — `scripts/e2e/telegram-viewport.mjs`. На телефоне игра фиксирует портрет |
| `TG-D` | Telegram Desktop, узкое окно | 420×640, затем 1280×720 | То же, `platform: "tdesktop"`, десктопный UA. В узком окне должна появиться плашка «Открыть в браузере» |

Правила эмуляции:

- В мобильных режимах **не пользуйтесь клавиатурой и hover**. Всё, что нельзя сделать касанием, — баг.
- В `TG-*` не предполагайте, что доступна вся площадь экрана. Считайте верхние и нижние safe-area и системную шапку Telegram занятыми.
- Поворот телефона проверяйте сменой размера `MP` → `ML` → `MP` в середине сценария, где это указано.
- В отчёте всегда указывайте режим и точный размер viewport.

## Общие проверки (применяются к КАЖДОМУ сценарию)

В сценариях они не повторяются. На каждом ключевом скриншоте проходите по списку:

1. **Понятность.** Можно ли понять, что делать дальше, не зная внутренней логики? Есть ли явное следующее действие?
2. **Доступность действий.** Основные действия видны и нажимаются. Ни одно ключевое действие не спрятано только за клавишей, hover или жестом.
3. **Нет тупиков.** Из любого состояния можно продолжить игру или выйти: нет модалки без закрытия, нет вечного «Ждём…», нет управления, которое перестало отвечать.
4. **Ввод.** Клик, tap, hover, drag, удержание работают и не срабатывают дважды. Tap не «проваливается» сквозь UI в 3D-сцену и обратно.
5. **Перекрытия.** Кнопки, панели, текст, тосты, подсказки и игровые объекты не перекрывают друг друга так, что что-то нельзя прочитать или нажать.
6. **Границы экрана.** Ничего не обрезано краем экрана, safe-area, «чёлкой» или шапкой Telegram. Нет горизонтальной прокрутки страницы.
7. **Читаемость.** Текст не меньше ~12 px на мобильных, контраст достаточен на тёмном фоне, нет обрезанных слов без многоточия и подсказки.
8. **Состояние игры.** Всегда видно, где я, какое время суток, что с моим персонажем, что происходит (бой, вылазка, совет, ожидание других).
9. **Интерактивность.** Интерактивные объекты заметны (подсветка, курсор, иконка). Неинтерактивное не выглядит как кнопка.
10. **UI не мешает игре.** Панели не закрывают персонажа, цель действия или важную часть сцены дольше, чем нужно.
11. **Touch-цели.** В мобильных режимах цели не меньше ~40×40 px (минимум 32 px для плотных списков) и не стоят вплотную друг к другу.
12. **Меню.** Открываются и закрываются предсказуемо: крестик, повторное нажатие кнопки, `Esc` на десктопе, «назад» в Telegram, где это уместно.
13. **Popup и контекстные меню.** Закрываются, и после закрытия управление персонажем возвращается.
14. **Сохранение состояния.** После перехода между экранами (меню ↔ сцена, бункер ↔ вылазка ↔ бой, поворот экрана, перезагрузка) состояние корректно: выбранное, введённое и найденное не теряется и не дублируется.
15. **Консоль.** Нет ошибок `pageerror` и `console.error`. Если есть — прикладывайте к любому найденному issue как доп. данные.
16. **Отклик.** Действие даёт видимый отклик меньше чем за ~150 мс (подсветка, звук, анимация), даже если результат приходит с сервера позже.

## Как оформлять результаты

### Скриншоты

- Делайте скриншот в **каждом ключевом состоянии**, которое перечислено в сценарии в пункте «Скриншот», и в момент любой найденной проблемы.
- Имя файла: `<ID>__<режим>__<шаг>.png`, например `COMBAT-UI-004__MP__03-target-selected.png`.
- Для анимаций и отклика допустима серия из 2–3 кадров с интервалом.

### Bug

Bug заводится, если проблема влияет на usability, gameplay, читаемость, responsiveness или consistency либо выглядит как явный дефект. Вкусовые предпочтения — не баги.

```markdown
**[BUG] <коротко, что не так>**
- Сценарий: <ID>
- Severity: Blocker | Major | Minor | Cosmetic
- Режим: <код> (<ширина×высота>, touch/mouse, браузер)
- Шаги воспроизведения:
  1. …
- Ожидалось: …
- Фактически: …
- Скриншот: <файл>
- Консоль/сеть: <если есть>
- Воспроизводимость: всегда / N из M / один раз
```

| Severity | Когда ставить |
|---|---|
| **Blocker** | Нельзя продолжить игру или пройти этап: тупик, краш, недоступное обязательное действие, потеря сохранения, игра не запускается в режиме |
| **Major** | Ключевая механика работает неправильно или ею практически невозможно пользоваться в режиме; неверные числа, влияющие на решения (например, `NaN%`); серьёзная потеря прогресса или ресурсов; важная кнопка перекрыта |
| **Minor** | Мешает, но есть обходной путь: неудобное расположение, отсутствие отклика, мелкая несогласованность, обрезанный второстепенный текст |
| **Cosmetic** | Визуальный дефект без влияния на игру: сдвиг на пару пикселей, мерцание, неровный отступ |

### Improvement

Если всё технически работает, но игровой опыт заметно лучше можно сделать **небольшим** изменением существующего — заводите improvement, не баг. Не предлагайте переделать игру или добавить большую систему без серьёзной причины.

```markdown
**[Gameplay Improvement | UX Improvement | UI Improvement] <коротко>**
- Сценарий: <ID>, режим: <код>
- Что сейчас происходит: …
- Почему это ухудшает опыт: …
- Небольшое изменение: …
- Скриншот: <файл> (если есть)
```

Особенно ищите:

- долгие однообразные действия;
- выборы, которые очевидны и не требуют решения;
- взаимодействия, состоящие из лишних кликов;
- результат действия, который плохо ощущается (нет цифры, звука, анимации, изменения мира);
- быстро повторяющийся игровой цикл;
- необходимость слишком часто открывать меню;
- последствия выбора, которые непонятны до выбора;
- механику, которая есть, но не добавляет интересного gameplay.

### Итог прогона

В конце прогона — таблица: `ID | режим | PASS / FAIL / BLOCKED / SKIPPED | issues`. `BLOCKED` — если не удалось дойти до предусловия (с причиной). `SKIPPED` — если режим к сценарию неприменим (с причиной).

## Приоритет прогона

Если времени мало, идите в таком порядке:

1. **Smoke (каждый прогон):** `BOOT-FLOW-001`, `LOBBY-FLOW-001`, `PROLOGUE-FLOW-001`, `BUNKER-FLOW-001`, `CTX-FLOW-001`, `CHORE-FLOW-001`, `BUILD-FLOW-001`, `COUNCIL-FLOW-001`, `SORTIE-FLOW-001`, `SCAVENGE-FLOW-001`, `COMBAT-FLOW-001`, `RETURN-FLOW-001`, `GMENU-FLOW-001`, `PERSIST-FLOW-001`, `END-FLOW-001`, `TG-FLOW-001`.
2. **Core UX:** все `*-UX-*` и `*-UI-*` в областях бункер, вылазка, бой, совет.
3. **Edge:** все `*-EDGE-*` и `CROSS-*`.
4. **Feel:** все `*-FEEL-*`. Их лучше проходить в длинной сессии (см. `FEEL-FLOW-001`): оценки игрового опыта требуют поиграть подольше.
